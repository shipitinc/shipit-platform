## 2. MULTI-PRODUCT ARCHITECTURE PRINCIPLES (HARD)

1. **Product identity is a first-class isolation/provenance boundary**, not a
   display label. All context loading, repository retrieval, artifact lookup,
   and evidence retrieval are scoped by `productId`.
2. **No `currentProduct` singleton.** No mutable global process variable.
   Verified: none exists today — S-1 must not introduce one (MP-AC-3).
3. **Operations on one Product must not pause or mutate another.**
   Supported shape: Product A ACTIVE + Product B ACTIVE + Product C ONBOARDING.
4. **Product status/lifecycle is per-Product** (`ProductState`:
   `draft → active | archived | deprecated`; onboarding writes a bounded
   bootstrap record).
5. **Context lookup is never ambiguous.** `ProductContext(productId)` loads
   exactly that Product; a fetched row whose scope does not match the requested
   `productId` is a **fault**, rejected at the boundary — never silently
   filtered.
6. **Avoid denormalized product identifiers where scope is safely derivable**
   (§4 table). Direct scope lives where an entity has no unambiguous parent;
   everything else derives through the owning chain.
7. **UI filtering is not the enforcement mechanism.** Product-scoped API calls
   are scoped at the API/domain boundary (explicit `productId` parameter).

## 3. PRODUCT IDENTITY (durable, unambiguous)

Product identity is durable and is **NOT** any of:
- current working directory
- repository URL
- repository path
- chat/session/agent execution
- any derived process-global

A Product may own **multiple `RepositoryReference`s**:

```
Product: TeamHub
  repositories: frontend, backend, infrastructure
Product: PartnerHub
  repositories: monorepo
```

Identity is a durable `productId` (uuid per existing `ProductManifest`
schema), independent of where the work happens to run.

## 4. PRODUCT ISOLATION MODEL — ENTITY SCOPE ANALYSIS

Legend: **DIRECT** = row carries authoritative `productId` (no unambiguous
parent to derive from). **DERIVED** = scope obtained through the owning chain,
no product column. **GLOBAL** = platform-level, no product scope. **N.A.** =
not applicable.

### 4.1 New S-1 entities

| Entity | Scope | Rationale |
|---|---|---|
| `Product` (registry row) | DIRECT (identity) | The scope root; durable `productId` + name + `ProductState` + manifest ref |
| `RepositoryReference` | **DIRECT** (`productId`) | A repo belongs to exactly one Product (TeamHub → frontend/backend/infra; PartnerHub → monorepo). One Product → N repos; one repo → one Product (S-1) |
| `ProductBaseline` | **DIRECT** (`productId`) | Per-Product pinned baseline (revision per RepositoryReference, build/test hash); independent per Product |

### 4.2 Existing + future governed objects

| Entity | Scope | Mechanism / rationale |
|---|---|---|
| `WorkItem` | **DIRECT** (`productId` — already exists, ALREADY_ALIGNED) | WorkItem is the scope *root of the derived chain* (jobs, executions, decisions, evidence, artifacts hang off it). It has no single mandatory parent Objective, so it anchors product identity itself. `productId` already persisted `NOT NULL` |
| `Objective` | **DIRECT** (`productId`) | Parent is the Product (no intermediate). MP-AC-11 defines the association |
| `Plan` | DERIVED (Objective → Product) | No product column; resolve via Objective |
| `Job` | DERIVED (WorkItem → Product) | `Job.workItemId` → `productId`. No new column. Scheduler provenance via join — MP-AC-12 |
| `WorkerExecution` | DERIVED (Job → WorkItem → Product) | Runtime receives product only inside its bounded execution-context envelope |
| `AgentExecution` | DERIVED (WorkItem → Product) | MP-AC-9. Runtime context includes explicit `productId` (§6); never a global |
| `HumanDecision` | DERIVED (workItemId → Product) | No column. Global Needs You aggregates via join and returns `productId`+`productName` per decision (provenance preserved) |
| `Defect` | **DIRECT** (`productId`) | A Defect may be reported against a Product *before* it has an affected WorkItem/Run. Direct on Defect is authoritative, not denormalized. MP-AC-10 |
| `DesignRevision` | DERIVED (DesignContract/WorkItem → Product) | Design authority (Penpot workspace membership) is per-Product |
| `ArtifactReference` | DERIVED (owning WorkItem → Product) | Lookup enforces product scope. Storage key carries product namespace for future GCS authorization — MP-AC-15 |
| `QA evidence` | DERIVED (WorkItem → Product) | Retrieval scoped by owning Product |
| `CompletionAssessment` | DERIVED (Objective → Product) | Future (005 §4.6) |
| `ReadinessAssessment` | DERIVED (Objective → Product) | Future |
| `Environment`/deployment refs | DERIVED (Product's manifest) | `EnvironmentConfig` lives on the Product's manifest; deployment refs resolve via WorkItem |

### 4.3 Global / N.A.

- **GLOBAL:** worker registry + capabilities, scheduler infrastructure
  (queue/claim/lease mechanics), platform tokens (referenced by name only,
  AGENTS.md §13), global observability surfaces.
- **N.A.:** pure enums (`WorkItemState`, `AgentRole`, `JobType`,
  `WorkItemCategory`), platform-neutral contracts.

### 4.4 Rules derived from the table

- A `productId` column belongs **only** on: `Product`, `RepositoryReference`,
  `ProductBaseline`, `Objective`, `Defect`, and existing
  `WorkItem.productId`. Never on `Plan`, `Job`, `WorkerExecution`,
  `AgentExecution`, `HumanDecision`, `DesignRevision`, `ArtifactReference`,
  evidence, assessments.
- Every WorkItem-rooted lookup (jobs, decisions, evidence, artifacts,
  executions) is parameterized by the owning WorkItem's `productId` **at the
  API/domain boundary**.
- Context lookup fault semantics: if a store row's derived Product ≠ requested
  Product → reject (500/fault or 403), never silently return another Product's
  data.

## 5. CROSS-PRODUCT CONTAMINATION THREAT MODEL

Goal: a PartnerHub execution must never receive TeamHub requirements, repo
files, baseline, design authority, artifacts, Defects, WorkItems, QA evidence,
HumanDecisions, environment config, credentials/secrets, or release policy —
and vice versa.

| Vector | Mitigation (S-1 enforces / future) |
|---|---|
| SQL scope leak | Every product-scoped store query parameterized by `productId` (or derived for WorkItem-rooted lookups). Backed with contract + security tests (MP-QA) |
| Repository retrieval | `RepositoryReference` is `productId`-scoped. `git_worktree_workspace_manager` (already pins to an explicit revision) must also validate the requested repository belongs to the requesting Product before creating a worktree — documented as **S-1 boundary**, enforced in onboarding (descriptor writes `productId`) and validated at retrieval |
| ArtifactReference lookup | Resolve artifacts only within the owning WorkItem's Product (or the explicit requesting Product). Never raw URI dereference |
| Evidence retrieval (future QA) | QA evidence row → WorkItem → Product; store method takes `productId` and rejects mismatch |
| HumanDecision / Needs You | Global aggregation returns per-decision `productId`/`productName` (provenance); product-scoped filter at API boundary |
| Design authority | Per-Product design-authority record binding to that Product's Penpot workspace; token is profile-wide (AGENTS.md §13) but **membership/role scoping** governs which workspace a Product may touch |
| Environment config | Part of the Product's manifest, not shared implicitly |
| Credentials/secrets | Never in `ProductBaseline`; reference-named only (AGENTS.md §13); a worker receives only the executing Product's credential refs (§9) |
| Release policy | Per-Product (deploy gates already machine-enforced; scope them by Product) |
| Worktree overlap | Worker runtime must not host two Products' work in one lease (existing lease/worktree isolation preserved; `productId` added to the execution-context envelope) |

**Principle:** ProductContext loading is **explicit and bounded** —
`load(productId)` returns exactly one Product; no inferred "current" context.

## 6. AGENT EXECUTION CONTEXT (future, model now)

Conceptual chain (S-1 designs, S-3+ realizes):

```
AgentExecution
  → WorkItem / bounded task
  → Objective (where applicable)
  → Product
```

- An agent never depends on a mutable global `CURRENT_PRODUCT`. Processes may
  execute work from different Products concurrently.
- Execution-context envelope carries `productId` explicitly (bounded
  `ProductContext(productId)`), handed to the worker with the execution request
  — not read from a process-global.
- S-1 impact: onboarding writes a `WorkspaceDescriptor` that encodes
  `productId` + `RepositoryReference`, so the future execution layer can build
  the bounded context from durable records alone (005 §3.1 invariant 3).

## 7. ORCHESTRATOR MODEL (future, recorded now)

Do **NOT** architect one long-lived conversational orchestrator session holding
every Product's context. The pattern:

```
request/execution
  → identify product
  → load bounded ProductContext(productId)
  → reason
  → persist typed result
  → terminate
```

- Another execution may do the same for another Product **concurrently**.
- Chat/session history is **not** the isolation mechanism (AGENTS.md §3).
- Extends 005 §4.9/§7 (orchestrator contract) without modification; adds the
  product-scoping clause.

- Future workers receive **only the executing Product's** credential refs
  (AGENTS.md §13: referenced by name, injected by secret manager).
- S-1 identifies the boundary and encodes it in the reference model; secret
  management implementation is deferred (005 §11 deferred list).

## 11. MULTI-PRODUCT SCHEDULER IMPLICATIONS (S-1 = analysis only)

Verified current state:
- `Job` carries `workItemId`, `jobType`, `requiredRole`, capabilities,
  priority, state, dedupeKey, attempt/maxAttempts, timestamps — **no product
  field** (`packages/platform_contracts/lib/src/types/job.dart`).
- `runnable_work` routes "next" by entry-state; the queue is claim-CAS/lease
  reconciled; **no contract assumes or enforces a single Product** — but
  nothing expresses Product either.
- A Job's **product provenance is already derivable**: `job.workItemId →
  work_item.productId`. No schema change needed for provenance.

**S-1 decision:** do **not** redesign the scheduler. S-1 only guarantees that
Product identity propagates to every governed Job via its WorkItem anchor, so a
later scheduler slice can read provenance directly.

**Documented migration/evolution (future slice, not S-1):**
- `JobQueue` gains product-scoped read/summary views (join on WorkItem).
- `Scheduler.pickNext` may become product-aware: per-Product `runnableCount`,
  fairness, priority tiers, capacity allocation, operator override.
- Resource-policy problem example recorded: TeamHub(30 runnable) vs
  PartnerHub(2 runnable) under a global FIFO could let TeamHub monopolize
  capacity → future policy may add **product priority / per-product
  concurrency / fairness / capacity allocation / operator override**.
- NOT implemented in S-1; only the propagation guarantee is an S-1 acceptance
  criterion (MP-AC-12).

## 12. GLOBAL ATTENTION IMPLICATIONS (recorded, not built in S-1)

Two surfaces must coexist:

  PartnerHub  – Approve migration plan
  TeamHub     – Clarify subscription behavior

- **PRODUCT-SCOPED WORK SURFACES:** unit of attention within a Product

- **GLOBAL HUMAN ATTENTION:** aggregates gates across Products while preserving
  clear provenance.

Data/API implications (future):
- `HumanDecision` stays DERIVED (workItemId → Product); no column.
- The pending-decisions read path returns `productId` + `productName` per
  decision and supports an explicit `?productId=` filter at the API boundary.
- Needs You UI groups by Product. Not implemented in S-1.

## 13. CONTROL-PLANE SCOPE + PRODUCT SELECTOR (recorded, not built in S-1)

- **GLOBAL scope** eventually answers: which Products are active, what needs
  human attention across all Products, how much work is executing.
- **PRODUCT scope** eventually answers: what TeamHub is doing, what remains for
  its objective, what is blocked, its readiness state.
- **Product selector** (future UI): explicit current Product context. **Never
  client-side filtering** as the security boundary — product-scoped endpoints
  are explicitly scoped at the API/domain boundary; a screen must never render
  another Product's data from stale client state.
- IA implication: Home/global observability + per-Product surfaces coexist;
  recorded here for the future IA slice (005 §5.3), not built in S-1.
