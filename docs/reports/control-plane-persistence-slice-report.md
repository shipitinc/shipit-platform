**`migration_persistence_test.dart` (4)** — migration-level assertions:
(1) `job_active_dedupe_unique` index exists with the right predicate; (2) two

**`endpoints_persistence_test.dart` (5)** — `workflowEndpoints.inspect`,

`workerEndpoints.listExecutions`/`inspect`, `executionEndpoints.list`/`inspect`

to `designApproved`, replays idempotently, and timestamps serialize as ISO-8601

**`e2e_restart_persistence_test.dart` (7)** — a `Harness` is a "process";
constructing a fresh one over the same Postgres rows simulates a crash-and-
restart with no shared in-memory state:
- Workflow restart: state + transition history reconstruct and continue.
- Claim-crash: persisted claim never dispatched → requeued → exactly one
  dispatch; event stream is `queued→claimed→queued→claimed→dispatched→completed`,
  one `jobDispatched`.
- Running worker under restart: lease is renewed, job stays `running`, zero new
  dispatches.
- Finished-but-not-adopted: outcome adopted, no new execution.
- Decision durability: pending blocking decision + gate survive restart, are
  resolved in the new process, and a duplicate resolution replays idempotently.
- Idempotent transition replay: a repeated idempotency key adds no history.
- Orphan store read: a non-terminal execution re-hydrates intact (not
  prematurely finalized by reads).

## 6. EVIDENCE (Deterministic Proofs)

1. **Postgres = the same contracts as memory/file.** The exact shared suites
   pass against both the in-memory stores and the Postgres stores (32/32), so
   file-store behaviour and Postgres behaviour are the same contract.
2. **No lost write.** `saveWorkItem`/job saves are guarded `UPDATE` with
   affected-rows check; a stale `expectedVersion` is rejected
   (`ConcurrentModificationException`/`ConcurrentJobModificationException`)
   exactly as the CAS tests demand.
3. **At-most-once claim.** Two actors racing one claim against Postgres: one
   in-transaction `UPDATE ... WHERE state='queued'` wins, one owner.
4. **Dedupe enforced by the database.** The partial unique index
   `job_active_dedupe_unique` makes two active jobs with the same
   workItemId/state/jobType/role impossible; terminal jobs release the slot.
5. **No double-resolve.** Two processes resolving the same `HumanDecision`:
   first wins, second replays the same result, state moves exactly once.
6. **Full-resume from rows.** Process-restart proofs re-hydrate fresh engine/
   scheduler/stores from Postgres and reconstruct every durable boundary,
   including idempotent re-play of transition and decision operations.
7. **Endpoints never set state.** Endpoint reads return `.toJson()` shapes of
   durable records; the only write endpoint delegates to
   `resolveHumanDecision`.

## 9. POSTGRES SCHEMA (Migration)

One Serverpod migration (`control_plane/server/migrations/20260914041810984/
migration.sql` + `definition.sql`) creates every platform table on Postgres:
`work_item`, `work_item_transition`, `human_decision`, `job`, `job_claim`,
`scheduler_event`, `worker_registration`, `worker_execution`, `worker_result`,
`worker_event`, `agent_execution_request`, `agent_execution`, `agent_event`,
`agent_result`, `platform_verification`. Storage rules:

- Nested domain structures persist as JSON `text` columns (`*Json`); stores
  pass raw decoded maps/lists through (never pre-typed objects).
- `timestamp without time zone` stores UTC wall-clock; `decodeUtc` re-reads it
  as UTC.
- `job_active_dedupe_unique` — `CREATE UNIQUE INDEX ... ON job(dedupeKey)
  WHERE state IN ('queued','claimed','running','retryWaiting')` is appended to
  the migration. Serverpod's boot compare warns "Missing Index
  job_active_dedupe_unique" until the index generator knows it natively; the
  warning is benign and asserted by the migration test.
- `work_item_version` / `job_version` back the CAS guards; `dedupeKey` is
  `NOT NULL`.

## 11. DATABASE-LEVEL DEDUPE

The scheduler dedupe key (`<workItemId>:<state.wire>:<jobType.wire>:<role.wire>`,
ADR 0016) is now enforced by Postgres itself. The partial unique index makes a
duplicate active job a `duplicate key` violation at insert time — impossible to
race past even with multiple replicas. Terminal states leave the index
predicate, releasing the key for the next workflow-state window. Two inserts
sharing an active key: the first wins, the second throws, count stays 1.

## 12. CAS & MULTI-REPLICA RACE

Postgres keeps the scheduler/workflow-store CAS semantics:

- `saveWorkItem` = `UPDATE ... WHERE "workItemId"=@id AND "version"=@expected`;
  zero affected rows → either `ConcurrentModificationException` (stale) or an
  `INSERT ... ON CONFLICT DO NOTHING` path for fresh items.
- Job saves and claims use the same guarded pattern; `claim()` additionally
  requires `state='queued'` in the same transaction.
- The concurrency suite proves stale-CAS rejection, dedupe-write convergence,
  claim ownership, and double-resolve convergence — deterministic (no sleeps),
  via racing stores each on their own session over the single shared DB slot.

---

## 13. TRANSACTION WRAPPING

Every multi-write durable flow runs in one server-side transaction:

- `DurableWorkflowEngine.transition` — state + history + blocking-decision
  writes atomic; `requestHumanDecision`/`resolveHumanDecision` atomic.
- `JobQueue` — `claim` (state→claimed + claim row), `complete`/`fail`/`cancel`,
  `revertToQueued`, `adoptResult` (job + event + result adoption) atomic.
- `LocalWorker` — `markRunning` + dispatch handoff, `_finish` outcome
  recording atomic.
- `ExecutionCoordinator` — `_createExecution`, orphan path, `_finalize`
  success/catch atomic (via `ExecutionStore.inTransaction`).

App-level `inTransaction` is on the store interfaces so file protocols behave
identically; Postgres runs the real eager transaction.

## 14. ENDPOINTS ARE READ-ONLY (NEVER SET STATE)

`WorkflowEndpoints` (inspect, listDecisions), `SchedulerEndpoints` (listJobs,
inspect), `WorkerEndpoints` (listWorkers, listExecutions), and
`ExecutionEndpoints` (list, inspect) return `toJsonObject`/`toJsonList` shapes
of durable records. `WorkflowEndpoints.resolveDecision` is the one behavioral
endpoint and delegates to `DurableWorkflowEngine.resolveHumanDecision`, which
routes through the validated `Transition` table (`designApproval+approve →
designApproved`, etc.). There is no path from an endpoint to
`WorkItem.state = ...`; `control_plane/server` never imports a state setter.
Serverpod lacks a generic `ServerpodException`, so endpoint errors are
structured-logged and re-thrown — the server never fabricates HTTP semantics
for domain errors.

---

## 15. HUMAN DECISION DURABILITY

`HumanDecision` objects are pure Postgres rows (never memory-only): the
decision includes `decisionId`, `workflowId`, `decider`, `choice`, `rationale`,
`timestamp`, and `signature` (algorithm/publicKey/signature/signedAt). A
blocking decision parks the work item in `waitingForHumanDecision`; a fresh
process re-hydrates the pending decision and the gate from rows, resolves it to
`designApproved`, and replays a duplicate resolution idempotently. Endpoints
expose pending decisions read-only; resolution is the single write path.

## 16. STRUCTURED LOGGING

`StructuredLogger` writes key=value career events through Serverpod
`session.log` (which lands in Postgres): each endpoint request emits
`control_plane.inspect`, `workflow.decision_resolved`, and error events with
level + exception + stack trace, so the durable audit trail is observable by
the same read-only endpoints.

## 17. PROCESS-RESTART SEMANTICS (E2E)

The scheduler's lease reconciliation (ADR 0016) operates over Postgres:

| Persisted state | Restart action (proven) |
|---|---|
| Claimed, no durable executionReference | requeued → re-claimed → exactly one dispatch |
| Claimed, live non-terminal `WorkerExecution` | lease renewed, job stays `running`, zero new dispatches |
| Claimed, durable terminal `WorkerExecution` | outcome adopted into the job |
| Workflow mid-gate (blocking decision pending) | decision + gate re-hydrated; resolved once, replays idempotent |
| Transition with a seen idempotency key | no-op, history unchanged |
| Non-terminal `AgentExecution` | re-hydrates intact; finalized only by an owning coordinator |

## 18. DETERMINISM MECHANISM

No sleeps, no timers. The Postgres harness is fully scripted: each test
constructs its own stores/engine/scheduler over the shared schema and drives a
scripted `FakeDispatch` (like the scheduler package's `ControlledDispatcher`)
whose `run()` completes synchronously by flushing a `WorkerExecutionResult`.
The clock is an injectable `DateTime Function()` with a fixed `t0`/`t1`, so
lease expiry, orderEligible, and claim windows are exact. Running a parallel
runner re-introduces nondeterminism through TRUNCATE collisions, so the suite
is pinned to `dart test -j 1`.

## 27. INDEPENDENT REVIEW (Adversarial Trace)

Reviewer re-examined the highest-risk invariants independently of the author:

1. **"Can a second scheduler replica create a duplicate active job?"** — Traced
   `enqueueIfAbsent` on Postgres: dedupe check inside the same transaction that
   inserts, plus the `job_active_dedupe_unique` partial index as the DB-level
   backstop. A race yields a `duplicate key` violation on the index — the insert
   is aborted, never a silent second job. Confirmed unconditionally safe even if
   the app-level check were removed.
2. **"Can an endpoint move state?"** — Grep of `control_plane/server` for
   `WorkItemState`/`transition(`/`state =` shows reads only; the single write
   endpoint calls `DurableWorkflowEngine.resolveHumanDecision`, which routes
   through the `Transition` table and never accepts a target state from the
   request. Confirmed.
3. **"Is a live execution double-dispatched after a crash?"** — Traced restart:
   expired lease + durable non-terminal `WorkerExecution` → reconcile renews,
   the job stays `running` and is not eligible, and the E2E test asserts zero
   new `jobDispatched` events. Confirmed.
4. **"Is a lost write possible?"** — Guarded `UPDATE ... WHERE
   "workItemId"=@id AND "version"=@expected` returns zero rows on a stale
   writer; the row aborts and nothing is overwritten. The concurrency suite
   observed the loser diverge, not the canonical row. Confirmed.
5. **"Can duplicate resolution double-move a gate?"** — The concurrency double-
   resolve test and the E2E replay both assert the item lands in `designApproved`
   exactly once with a single history entry. Confirmed.
6. **"Does TRUNCATE-cleanup make the suite order-dependent?"** — Every suite
   seeds via the public store/engine APIs inside its own group with row-scoped
   expectations; `-j 1` + per-setUp TRUNCATE makes order irrelevant. Confirmed.

**Review verdict: P0/P1 clean — no blocking findings.** Residual items are all
deferred-by-design (transport, PKI, auth, pagination, UI).
